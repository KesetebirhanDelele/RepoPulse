# The Colaberry Agent Blueprint System
**Developer Introduction**

---

## What it is

A structured approach to building software with AI coding agents and junior developers working together. It produces a complete system design — across 11 layers covering design, build, operation, and evolution — before a single line of code is written. The same files that teach junior developers what they are building also give Claude Code the navigation index it needs to work efficiently without re-exploring the codebase every session.

---

## The problem it solves

Building with AI agents and junior developers has two failure modes that pull in opposite directions:

- **Junior developers** need breadth — they need to understand the whole picture, why each decision was made, and what they are expected to build before they touch code
- **AI coding agents** need precision — they need to find the right file fast, read only what is relevant, and not waste context on files that don't apply to the current task

Most teams solve one at the cost of the other. Verbose documentation helps juniors but bloats AI context. Sparse AI-optimized instructions leave junior developers without guidance. This system solves both with the same set of files.

---

## The 11-Layer Framework

Every project is designed across 11 layers grouped into 4 zones. Not every layer applies to every project — scope and project type determine which layers are required.

```
DESIGN ZONE — What are we building and how should it behave?
  Layer 1  Requirements       What the system must do
  Layer 2  Specifications     Data models, APIs, architecture
  Layer 3  Directives         Business rules and behavior rules per capability

BUILD ZONE — How do we build, test, and track it?
  Layer 4  Execution Plan     Build order, milestones, dependencies
  Layer 5  State Model        System states, transitions, invalid transitions
  Layer 6  Test Scenarios     Validation flows, edge cases, failure scenarios

OPERATE ZONE — How does it run and recover in the real world?
  Layer 7  System Loop        Background jobs, triggers, scheduling
  Layer 8  Failure Playbook   What happens when things go wrong
  Layer 9  Environment        Dev/staging/prod config, secrets, feature flags

ADAPT ZONE — How does it change safely over time?
  Layer 10 Data Lifecycle     Retention, mutation rules, deletion, audit trail
  Layer 11 Evolution Strategy Versioning, migrations, rollback, safe rollout
```

**UX** is not a standalone layer. It is embedded within each zone — user flows in DESIGN, UI state models in BUILD, error messages in OPERATE, design system evolution in ADAPT. For UI-first production systems, a consolidated `ux/interaction-model.md` is generated.

## The File Structure

```
spec/           Layer 1 and 2 — requirements and structure
directives/     Layer 3 — one file per capability
execution/      Layer 4 — build plan
state/          Layer 5 — state model
tests/          Layer 6 — test scenarios
runtime/        Layer 7 — system loop
failure/        Layer 8 — failure playbook
environment/    Layer 9 — config and secrets model
data/           Layer 10 — data lifecycle
evolution/      Layer 11 — evolution strategy
ux/             UX model (UI-first production only)
docs/           Junior developer onboarding guide
meta/           Claude Code navigation index
```

Files use numbered prefixes (`01-requirements.md`, `03-scoring-rules.md`) so junior developers know what order to read without being told.

---

## How the files are generated

A prompt-based blueprint generator (`system_architecture_file_generator_v3_2`) takes a project description and produces one file at a time on demand. It classifies the project, assesses the input, asks clarifying questions only when needed, and generates each layer file with appropriate depth based on project type and scope (MVP / Standard / Production).

The final file it generates is `meta/layer-artifacts.md` — a table mapping every layer to its file path, formatted for direct insertion into `CLAUDE.md`.

---

## The 5 Governance Files

These files are copied once per project and reused across all projects. They are not generated by the blueprint generator and are not modified by `/init`.

| File | Purpose | Who reads it |
|---|---|---|
| `CLAUDE.md` | Repo-specific context for every Claude Code session — commands, architecture, Layer Artifacts table | Claude Code, every message |
| `AGENTS.md` | Claude's 4 operational roles, testing rules, approval gates, 11-layer folder map | Claude Code at session start |
| `directives/progress-tracking.md` | PROGRESS.md governance — session startup rules, maturity assessment, definition of done | Claude Code |
| `directives/README.md` | Index of all directives with layer coverage | Claude Code, developers |
| `docs/onboarding.md` | Explains all 11 layers to junior developers — what each is, why it exists, how to use it | Junior developers only, never Claude Code |

---

## How Claude Code fits in

Claude Code operates in 4 roles in sequence for every task:

1. **Explore** — reads `CLAUDE.md`, navigates directly to the relevant layer files via the Layer Artifacts table. No repo scanning.
2. **Plan** — reads the relevant directive, designs tests first, identifies approval gates
3. **Build** — writes the minimum necessary code, stays in the correct layer
4. **Verify** — runs tests, confirms behavior matches the directive, updates `PROGRESS.md`

`PROGRESS.md` is the live maturity scorecard — it tracks how complete each capability is across all 11 layers and provides continuity between sessions so Claude Code never starts from scratch.

---

## What junior developers get

- `docs/onboarding.md` — one document that explains the entire 11-layer framework with plain-language descriptions of what each file is for and how to work within it
- Numbered files in reading order so the build sequence is obvious
- Directives that make business rules explicit before code is written
- A `PROGRESS.md` that shows exactly what is done, what is partial, and what is next

## Token Savings

Claude Code loads `CLAUDE.md` on **every message** in every session. Every token saved there compounds across the entire project lifetime.

### Per-file token cost (measured)

| File | Words | Tokens | Loaded |
|---|---|---|---|
| Old CLAUDE.md (monolithic) | 2,565 | ~3,500 | Every message |
| New CLAUDE.md (lean template) | 485 | ~650 | Every message |
| AGENTS.md | 1,007 | ~1,300 | Session start / non-trivial tasks |
| directives/progress-tracking.md | 862 | ~1,100 | Session start |
| docs/onboarding.md | ~800 | ~1,000 | **Never — human only** |

### Session cost comparison

| Scenario | Old system | New system | Saving | Reduction |
|---|---|---|---|---|
| Per message (CLAUDE.md load) | ~3,500 tokens | ~650 tokens | ~2,850 tokens | 81% |
| Session startup (orientation) | ~12,000–17,000 tokens | ~5,000–6,000 tokens | ~7,000–11,000 tokens | ~55–65% |
| Per task (finding relevant files) | ~3,000–12,000 tokens | ~500–2,000 tokens | ~2,500–10,000 tokens | ~75% |
| 30-message session total | ~117,000–122,000 tokens | ~24,000–26,000 tokens | ~93,000–96,000 tokens | ~79% |
| 100-message session total | ~362,000–372,000 tokens | ~70,000–76,000 tokens | ~292,000–296,000 tokens | ~80% |

### Where the savings come from

| Source | Old behavior | New behavior |
|---|---|---|
| CLAUDE.md size | 3,500 tokens every message | 650 tokens every message |
| Session startup | Claude scans repo + reads multiple files to orient | Claude reads Layer Artifacts table → jumps directly to relevant files |
| Per-task reads | 3–8 exploratory reads to find relevant code | 1–3 directed reads via Layer Artifacts table |
| Onboarding doc | N/A | Zero tokens — never read by Claude Code |
| AGENTS.md and directives | Embedded in CLAUDE.md, loaded every message | Separate files, loaded only when needed |

The 80% reduction is not a one-time saving. It applies to every message in every session across every developer's machine for the lifetime of the project.

## The workflow end to end

```
New project
    │
    ├── Run blueprint generator → produces 11 layer files + meta/layer-artifacts.md
    ├── Copy CLAUDE.md template → fill project name, paste Layer Artifacts table
    ├── Copy AGENTS.md, directives/progress-tracking.md, directives/README.md as-is
    ├── Run /init in Claude Code → fills commands, architecture, key files in CLAUDE.md
    │
    └── First Claude Code session
            ├── Claude reads CLAUDE.md, AGENTS.md, creates PROGRESS.md
            └── All future sessions: Claude navigates via Layer Artifacts table,
                reads only the files relevant to the current task,
                updates PROGRESS.md after every meaningful change
```

## Design principles

- **Two audiences, one system.** Every layer file teaches junior developers and directs Claude Code. No file exists only for one.
- **Intent before implementation.** All 11 layers are designed before code is written. The system is understood before it is built.
- **Capability maturity over code presence.** Progress is measured by how complete a capability is across the relevant layers — not by whether code exists.
- **Deterministic execution, probabilistic planning.** Claude reasons and plans. Scripts and tests execute. The two roles never mix.
- **Token efficiency by design.** Governance content is separated from repo-specific context. Claude reads only what it needs, when it needs it.
